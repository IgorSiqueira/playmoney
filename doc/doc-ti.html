Manual Técnico — PlayMoney

Documentação de infraestrutura, banco de dados e operação do sistema PlayMoney — plataforma de apostas em performance própria no Dota 2. Destinado à equipe de TI e desenvolvedores responsáveis por deploy, manutenção e suporte técnico.

Arquitetura

Internet │ ├── Next.js App (porta 3000) │ ├── /app/(dashboard)/ → páginas SSR (React Server Components) │ ├── /app/api/ → API routes (Edge-compatible handlers) │ └── /lib/ → auth, prisma, odds, bet-events, redis… │ ├── PostgreSQL (porta 5432) │ └── Pool de 10 conexões via pg.Pool → @prisma/adapter-pg │ ├── Redis (porta 6379) │ └── Rate limiting por IP/userId com TTL em milissegundos │ └── OpenDota API (HTTPS externo) └── Circuit breaker: CLOSED → OPEN (5 falhas) → HALF_OPEN (probe 30 s)

Deploy

Docker Compose (produção)

O projeto tem Dockerfile e docker-compose.yml prontos. Serviços: app (Next.js), postgres e redis.

# Pull das mudanças e rebuild
git pull
docker compose build app
docker compose up -d app

# Verificar logs
docker compose logs -f app

# Status de todos os serviços
docker compose ps

Quando rodar migrations

Importante
Migrations são necessárias somente quando o arquivo prisma/schema.prisma é alterado. Mudanças de lógica de negócio, UI ou API não requerem migration. 
# Verificar se há migrations pendentes
docker compose exec app npx prisma migrate status

# Aplicar migrations pendentes
docker compose exec app npx prisma migrate deploy

Rollback

# Restaurar imagem anterior (se usando tags)
docker compose stop app
docker tag playmoney-app:previous playmoney-app:latest
docker compose up -d app

# Via git (rebuild da versão anterior)
git checkout <commit-hash>
docker compose build app && docker compose up -d app

Constraints de integridade críticos

GameProfile @@unique([externalId, game]) — um Steam ID não pode ser vinculado a duas contas distintas (anti-hedge). Wallet é criada automaticamente no registro do usuário. Bet.gameProfileId é NOT NULL — toda aposta exige perfil Steam vinculado.

Migrations

# Criar nova migration (dev local)
npx prisma migrate dev --name nome-descritivo

# Aplicar em produção (sem gerar arquivo)
npx prisma migrate deploy

# Verificar status
npx prisma migrate status

# Reset completo (DEV ONLY — destrói dados)
npx prisma migrate reset
Produção
Nunca execute migrate reset em produção. Sempre faça backup antes de migrate deploy.

Autenticação

NextAuth v5 com estratégia JWT (sem tabela de sessões no banco). A config é dividida em dois arquivos para compatibilidade com o Edge Runtime do Next.js:

ArquivoResponsabilidade
src/lib/auth.config.tsProviders, callbacks — compatível com Edge
src/lib/auth.tsInstância com PrismaAdapter — somente Node.js

O role do usuário (USER / ADMIN) é embutido no token JWT no callback session. Para tornar um usuário admin, atualize diretamente no banco:

-- Promover usuário a admin
UPDATE "User" SET role = 'ADMIN' WHERE email = 'email@dominio.com';
Token em cache
O JWT fica no cookie do browser por 30 dias. Após promover um usuário, ele precisa fazer login novamente para o token refletir o novo role.

Rate limiting usa Redis quando REDIS_URL está configurada. Sem Redis, o contador é em memória por processo — não é compartilhado entre múltiplos containers. Em deploy com mais de 1 instância, Redis é obrigatório.

Connection Pool

O Prisma usa pg.Pool via @prisma/adapter-pg. O pool é criado uma vez na inicialização do processo e reutilizado via globalThis em desenvolvimento (evita múltiplos pools no hot-reload).

ConfigEnv VarPadrãoDescrição
maxDB_POOL_MAX10Conexões simultâneas máximas
idleTimeoutMillisDB_IDLE_TIMEOUT_MS30 000Fecha conexão ociosa após N ms
connectionTimeoutMillisDB_CONNECT_TIMEOUT_MS5 000Erro se não conectar em N ms
Tuning
Para Supabase ou conexão via PgBouncer, mantenha DB_POOL_MAX baixo (2–5). Em conexão direta ao PostgreSQL, 10–20 é adequado para tráfego moderado.

Circuit Breaker (OpenDota)

Implementado em src/lib/opendota.ts. Protege o sistema contra falhas em cascata da API externa.

EstadoCondição de entradaComportamento
CLOSEDNormal (padrão)Todas as requisições passam
OPEN5 falhas consecutivasRejeita requisições imediatamente; tenta probe após 30 s
HALF_OPEN30 s após OPENDeixa 1 requisição passar; sucesso → CLOSED, falha → OPEN
Estado em memória
O circuit breaker é por processo. Em múltiplas instâncias, cada uma tem seu próprio contador. Para estado compartilhado, seria necessário mover para Redis.

Redis / Cache

Usado exclusivamente para rate limiting. O cliente é criado em src/lib/redis.ts com fallback automático para mapa em memória quando REDIS_URL não está definida. Em produção sem Redis, é logado um aviso no startup.

# Testar conexão com Redis
docker compose exec redis redis-cli ping
# → PONG

# Ver chaves de rate limit
docker compose exec redis redis-cli keys "rl:*"

Endpoint de Calibração

Disponível em GET /api/admin/calibration. Compara a probabilidade prevista pelo modelo de odds com a taxa de vitória real dos últimos 90 dias. Requer role ADMIN.

Resposta

{
  "totalBets": 234,
  "wonCount": 118,
  "overallWinRate": 0.504,
  "brierScore": 0.1832,           // < 0.20 = bom
  "brierInterpretation": "bom",
  "calibration": [
    { "predicted": 0.45, "actual": 0.47, "count": 43 },
    { "predicted": 0.55, "actual": 0.58, "count": 61 }
  ]
}

Com menos de 10 apostas, retorna { "insufficient": true }. O Brier Score ideal é próximo de 0.20.

Runbook

Ativar modo manutenção

# Via API (requer token de admin)
curl -X PATCH https://playmoney.wizardtech.com.br/api/admin/platform \
  -H "Cookie: <auth-cookie>" \
  -d '{"maintenanceMode": true, "maintenanceBanner": "Manutenção programada. Voltamos às 22h."}'

Expirar apostas pendentes (cron)

curl -X POST https://playmoney.wizardtech.com.br/api/maintenance/expire-bets \
  -H "Authorization: Bearer $MAINTENANCE_SECRET"

docker compose exec postgres psql -U playmoney playmoney
